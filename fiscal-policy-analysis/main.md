# 财政政策分析

> 覆盖赤字率/专项债/化债/土地财政等财政议题的快慢双轨分析框架。

# 工作流原则（最重要）

## 原则0：快慢双轨——先判断用户意图

收到财政问题时，先花 3 秒判断用户要的是"快速判断"还是"深度分析"：

| 用户信号 | 模式 | 输出 |
| --- | --- | --- |
| "大概/简单说说/怎么样/如何" 等概括性提问 | **快答** | 一句话结论 + 2-3个核心矛盾简要列表 |
| "分析/深度/全面/详细/展望/报告" 等要求详细输出 | **深度** | 走完整流程（时效自检→web search→主要矛盾抓取→正文） |

> 不确定时默认走深度。快答也不能跳过时效自检。

## 原则1：抓主要矛盾，不要泛泛而谈

**这个skill最常被滥用的方式**：用户问"当前财政情况"或"二季度财政展望"，模型把每个维度都过一遍，每段一两句话，看似全面实则没有重点。

**正确做法**：先识别一两个主要矛盾 → 围绕矛盾深入展开（配数据/政策/传导链） → 次要维度一笔带过或不提。

**五大识别信号**（详见 ref-08 §8.1）：

1. 政策定调变化（措辞变即矛盾）
2. 数据异常项（偏离趋势/季节性最大）
3. 市场分歧点（卖方分裂处）
4. 决策层关注焦点（政治局会议/部长讲话）
5. 传导链断点（财政→经济→市场哪个环节出问题）

## 原则2：数据来源——按题型分流

### 题型分流表

| 题型 | 强制搜索项 | state file 作用 |
| --- | --- | --- |
| **月度财政点评** | excel底稿 → iFind EDB → 财政部网站 | 框架参考 |
| **展望/前瞻** | 必须先web search | 仅作为"基础框架" |
| **最新政策解读** | 必须先web search | 提供历史措辞演变作为对比基准 |
| **历史/框架/概念性问题** | 可不搜，直接用skill+state file | 主要参考 |
| **跨skill协同** | 按本skill+monetary skill各自分流规则 | — |

## 原则3：动态信息检索（强制规则）

### 强制规则（按题型）

展望、前瞻、最新政策解读类必须先web search验证。

### 市场指标取数纪律

禁止凭印象给数字或区间。取数优先级：① 用户当次提供的excel/数据 → ② iFind EDB → ③ 主动询问用户。

## 数据保鲜机制

### 时效自检第一步（每次调用必须执行）

**每次收到与"当前/最新/展望/前瞻"相关的财政问题时，第一步算时间差**：

```
当前日期 - state file last_checked → 
 ≤ 7天 且无重大事件 → state file 可用
 > 7天 或 期间有政治局会议/ECW/重大政策 → 必须先 web search 验证
```

### state文件

财政指标的最新值建议维护一份本地缓存（如 `state/fiscal_indicators.yaml`）作为"唯一真实来源"，避免文档硬编码值过期。

### 触发更新的事件

| 事件 | 频率 | 操作 |
| --- | --- | --- |
| 两会预算报告发布（每年3月） | 年度 | 必须更新state文件 + 修改ref中关键数字 |
| 政治局会议、中央经济工作会议 | 季度/年度 | 更新政策定调措辞 |
| 月度财政数据公布（每月20-25日） | 月度 | 不更新state（仅在写点评时使用最新数据） |
| 重大化债政策（如12万亿框架） | 不定期 | 更新state + 增加changelog |
